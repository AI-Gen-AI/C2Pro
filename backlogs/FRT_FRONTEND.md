### Vercel Build Parity Follow-up (2026-04-09)

**Task**: `TASK-FRT-168`

**Root Cause**:

- `apps/web/package.json` still used `next build`, which selects Turbopack by default on Next.js 16.
- In this monorepo layout, the Turbopack production path failed workspace root inference (`Couldn't find the Next.js package ... from apps/web/app`) even though the Webpack production path was already green.

**Resolution**:

- Added a regression test in `apps/web/src/tests/integration/ci/S1-13-frontend-ci.integration.test.ts` asserting the production build command stays pinned to the verified Webpack path.
- Updated `apps/web/package.json` to use `next build --webpack` for production parity with the validated build path.

**Verification**:

- `pnpm vitest run src/tests/integration/ci/S1-13-frontend-ci.integration.test.ts`
- `pnpm build`

### Root Route Manifest Regression Follow-up (2026-04-10)

**Task**: `TASK-FRT-169`

**Root Cause**:

- The duplicate root route regression returned: both `apps/web/app/page.tsx` and `apps/web/app/(app)/page.tsx` claimed `/`.
- Next 16 emitted the grouped page bundle under `apps/web/.next/server/app/(app)/page.js`, but the root client-reference manifest remained at `apps/web/.next/server/app/page_client-reference-manifest.js`.
- With Vercel restoring the previous build cache before `next build`, the missing grouped manifest path surfaced during build trace collection as `ENOENT ... app/(app)/page_client-reference-manifest.js`.

**Resolution**:

- Added `apps/web/src/tests/integration/ci/TASK-FRT-169-root-route-manifest-parity.integration.test.ts` to fail if a grouped root page is reintroduced beside `app/page.tsx`.
- Deleted `apps/web/app/(app)/page.tsx` so `/` is owned by the intended public landing/auth redirect entry only.
- Added `apps/web/scripts/clean-next-build.mjs` and updated `apps/web/package.json` to clear `.next` before `next build --webpack`, preventing restored caches from keeping deleted route artifacts alive.

**Verification**:

- `pnpm vitest run src/tests/integration/ci/TASK-FRT-169-root-route-manifest-parity.integration.test.ts src/tests/integration/ci/S1-13-frontend-ci.integration.test.ts`

## 7. Audit Reports

### Frontend Integration Test Audit (TASK-REV-FRONTEND-001)

**Date**: 2026-04-07
**Status**: ✅ Stabilized (48/48 Files Passing)

#### Findings:

1. **Root Cause of ERR_INVALID_URL**: Node.js `fetch` implementation in Vitest/JSDOM does not support relative URLs. Any call to `fetch('/api/...')` throws `ERR_INVALID_URL` because it lacks an origin.
2. **Current Fix**: The project implemented a custom MSW shim in `apps/web/src/tests/shims/msw-node.ts` that overrides `global.fetch` and automatically prepends `http://localhost` to relative paths.
3. **act() Warnings**: Many integration tests (Shortcuts, Mobile Evidence) still emit React `act(...)` warnings. These occur when state updates (e.g., from `fireEvent.keyDown` on `window`) are not correctly wrapped or awaited.
4. **Axios Inconsistency**: `vitest.setup.ts` sets `axios.defaults.baseURL = "/api"`. This is relative and will FAIL in Node for any non-mocked request. It currently works only because integration tests predominantly use `fetch`.

#### Recommendations:

- **Stabilization**: Sprint 2 task should be created to wrap failing state updates in `act()` to eliminate console noise and potential race conditions.
- **Consistency**: Update `axios.defaults.baseURL` to `http://localhost/api` in `vitest.setup.ts` to provide a consistent origin for all HTTP clients in the test environment.
- **Maintenance**: Retain the `msw-node.ts` shim until a full migration to a real `msw/node` setup is feasible (currently blocked by ESM/CJS issues).
