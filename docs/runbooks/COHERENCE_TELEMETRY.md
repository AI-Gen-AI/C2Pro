# Runbook: Coherence Telemetry

**Owner:** AI Core Team
**Status:** Active
**Last Updated:** 2026-04-26

## 1. Overview

This runbook details the structured telemetry generated by the Coherence V1 engine. The primary goal of this telemetry is to provide deep insights into the performance and behavior of the coherence evaluation graph while strictly adhering to data privacy and residency requirements (e.g., EU-residency).

All telemetry is sent to **LangSmith** under the `c2pro` project.

## 2. Span-based Monitoring

The Coherence graph is instrumented with spans that correspond to the execution of individual nodes. This allows us to measure latency, success/error rates, and metadata for each step of the evaluation process.

### 2.1. Node Spans

Each of the following nodes in the graph emits a span upon execution:

- `prepare_context`
- `deterministic_evaluate`
- `rag_similarity_check`
- `cross_clause_eval`
- `scoring_arbiter`
- `format_output`

The `llm_semantic_evaluate` node is **intentionally not instrumented** at this time and will be added after full production rollout.

### 2.2. Allowlisted Span Attributes

To prevent any sensitive data (clause text, PII, etc.) from leaving the application, we enforce a strict allowlist of attributes that can be attached to spans. Any attempt to add an attribute not on this list will fail a CI contract test.

The allowlisted attributes are:

| Attribute Name                 | Type          | Description                                                    | Example                                 |
| ------------------------------ | ------------- | -------------------------------------------------------------- | --------------------------------------- |
| `coherence.node_name`          | `string`      | The name of the graph node being executed.                     | `deterministic_evaluate`                |
| `coherence.score_version`      | `string`      | The version of the scoring logic (`v0` or `v1`).               | `v1`                                    |
| `coherence.findings_count`     | `integer`     | The number of findings generated by the node.                  | `3`                                     |
| `coherence.rule_ids`           | `list[string]`| A list of unique rule IDs evaluated by the node.               | `["G6-01-C1", "G6-01-C2"]`              |
| `coherence.tenant_id`          | `string`      | The ID of the tenant for whom the evaluation is running.       | `a1b2c3d4-e5f6-7890-1234-567890abcdef` |
| `coherence.project_id`         | `string`      | The ID of the project being analyzed.                          | `p1q2r3s4-t5u6-7890-1234-567890abcdef` |

## 3. Alert Event Spans

In addition to node execution spans, a special "event" span is created whenever the `format_output` node generates a high-priority alert. This allows for direct monitoring and alerting on critical findings.

### 3.1. Alert Attributes

| Attribute Name                 | Type     | Description                                | Example        |
| ------------------------------ | -------- | ------------------------------------------ | -------------- |
| `coherence.alert.rule_id`      | `string` | The ID of the rule that triggered the alert. | `G6-04-A1`     |
| `coherence.alert.severity`     | `string` | The severity level of the generated alert.   | `high`         |
| `coherence.tenant_id`          | `string` | The tenant ID associated with the alert.   | `a1b2c3d4-...` |
| `coherence.project_id`         | `string` | The project ID associated with the alert.  | `p1q2r3s4-...` |

## 4. How to Use This Telemetry

### 4.1. Monitoring Latency

In LangSmith, filter for spans where `run_type = "chain"`. You can group by the `coherence.node_name` attribute to see the P50/P90/P99 latency for each node in the graph. This is critical for identifying performance bottlenecks.

### 4.2. Monitoring Errors

Filter for traces with `error = True`. Group by `coherence.node_name` to identify which nodes are failing most frequently.

### 4.3. Alerting on Critical Findings

Create a monitor in your observability platform (e.g., Datadog, Sentry) that triggers on LangSmith webhooks. Configure the webhook to fire when a span with `event_type = "alert"` is created.

**Example Alerting Logic:**
- **Trigger:** Webhook received for an event span.
- **Condition:** `metadata["coherence.alert.severity"] == "high"`
- **Action:** Page the on-call engineer for the AI Core Team.

This allows for near real-time response to the most critical findings generated by the Coherence engine.
